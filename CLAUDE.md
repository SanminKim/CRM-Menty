# CRM Менти

CRM школы менторства аналитиков 1С: путь человека от заявки до оффера, платежи студентов, расчёт с партнёром-блогером. Работает на своём сервере. Интерфейс и тексты — на русском.

## Как устроено

- **`web/index.html` — вся страница CRM.** Один файл без сборки. Новые возможности делаются здесь.
- **`web/server.js` — слой данных.** Даёт странице `window.claude` (база, пользователь, скачивание файлов) поверх API сервера и `window.crmServer` (учётные записи, выход). Подключается сервером перед скриптом страницы.
- **`backend/` — сервер на Django.** Хранит записи как документы (`Doc`), проверяет права (`store.py`), отдаёт изменения по номеру ревизии, принимает заявки с сайта, загружает резервную копию.
- **`web/dev/mock.js`** — подмена `window.claude` для просмотра страницы без сервера. Страница должна работать и с ней: `window.crmServer` там нет.

Версия страницы, опубликованная в Claude, больше не развивается. Ссылка на неё хранится в проекте Claude «CRM Менти», а не в репозитории: репозиторий публичный.

## Команды

```bash
pip install -r requirements.txt
python manage.py test backend              # тесты сервера
python manage.py makemigrations --check --dry-run
node --check web/server.js
node -e "new Function(require('fs').readFileSync('web/index.html','utf8').split('<script>')[1].split('</script>')[0])"   # синтаксис страницы
python e2e/run.py                          # сквозная проверка в браузере: сам поднимает сервер на пустой базе
```

## Как ведём разработку

Порядок работы взят из ECC (см. `.claude/ECC.md`) и подогнан под проект:

1. **План.** Для задачи крупнее мелкой правки сначала план: что меняем, какие файлы, риски, как проверим. Агент `planner` или команда `/plan`. План согласуется с владельцем до начала работы.
2. **Тест до кода**, где это возможно. Сервер: тест в `backend/tests.py`, который сначала падает. Страница: проверка в `e2e/run.py`.
3. **Реализация** минимальным изменением. Никаких функций «на вырост».
4. **Ревью** перед коммитом: `code-reviewer` для любого изменения, `django-reviewer` или `python-reviewer` для Python, `security-reviewer` для всего, что касается прав доступа, персональных данных, платежей и приёма заявок, `database-reviewer` для моделей и миграций.
5. **Проверка.** Тесты сервера и `e2e/run.py` проходят, миграции согласованы. Навык `verification-loop`.
6. **Коммит.** Работа ведётся в ветке, в `main` попадает после проверки. Push в `main` запускает тесты в GitHub и выкладку на сервер.

## Правила проекта

Если навык или агент из ECC расходится с этим разделом, действует этот раздел.

- **Тесты Django — встроенный раннер** (`manage.py test`, `django.test.TestCase`). Не переводите проект на pytest, factory_boy или DRF без запроса владельца.
- **Страница — один файл без сборки.** Не добавляйте React, сборщики и внешние библиотеки. Правило «много маленьких файлов» к ней не применяется.
- **Права проверяет сервер, а не страница.** Все правила — в `backend/store.py` (`Access`). Скрытая на странице кнопка не считается защитой: на каждое новое правило нужен тест в `backend/tests.py`, который делает запрос от имени ментора и партнёра.
- **Ментор читает и правит только своих студентов** (`mentorId` равен его записи в команде) и их встречи; источник и долю партнёра у студента меняет только администратор. **Партнёр читает только свой отчёт.**
- **Запись идёт под блокировкой состояния** (`store.lock()`): ревизии строго растут в порядке фиксации, поэтому опрос не пропускает изменения. Любая новая запись в базу делается через `store.write`, `store.delete` или `store.system_write`.
- **На странице CRM выполняются только два скрипта**: `web/server.js` и скрипт из `web/index.html`, их хеши попадают в заголовок Content-Security-Policy. Не добавляйте второй `<script>`, обработчики в атрибутах (`onclick=`) и внешние скрипты.
- **Данные студентов не попадают в репозиторий**: ни в код, ни в тесты, ни в примеры. Для примеров — вымышленные имена.
- **Секреты только через переменные окружения** (`.env`, в git не коммитится).
- **Формат резервной копии** (`crm-menti-backup`) — те же записи, что хранит сервер. При изменении набора коллекций обновите `backend/backup.py`, тесты загрузки и поднимите `version` на странице.
- **Сообщения коммитов — на русском**, первая строка говорит, что изменилось для пользователя.
- **Правки студента — только через `patchStudent`.** Сервер заменяет массивы (платежи, отклики, заметки, история) целиком, поэтому патч считается от свежей записи (перед правкой страница подтягивает её с сервера), а «Отменить» откатывает только свой элемент.
- **Всё, что попадает в разметку из базы, проходит через `esc()`**, включая идентификаторы и числа в атрибутах.
- **Массовые действия работают только над строками, которые сейчас видны в таблице.** Выбор хранится в `S.sel`, видимые строки — в `S.visible`.
- **Графики** — встроенный SVG без библиотек. Цвета рядов заданы токенами `--c1`, `--c2` и проверены на различимость для светлой и тёмной темы; при смене проверьте заново.
- **Студент удаляется только в корзину** (`trashStudent`, поле `deletedAt`). `delDoc("students", …)` вызывается только из корзины в настройках.
- **Каждое изменение платежей и стоимости пишет запись в `log` студента** (`logItem`, `withLog`) в том же патче, что и само изменение.
- **Telegram-бот** (`backend/telegram.py`) работает через webhook и пишет в базу только заявку и заметки человека, с которым говорит. Обращения к Telegram не делаются внутри транзакции и не должны ломать запись: сбой Telegram только пишется в журнал. К существующей карточке чат привязывается, только если совпал сам чат (`tgId`), а не введённый телефон. В уведомления не попадают телефоны и почта.
- **Этапы воронки** заданы в двух местах: `STAGES` в `web/index.html` и `STAGES` в `backend/reports.py`. Меняются вместе; расхождение ловит тест `test_stage_list_matches_the_page`.
- **Отчёт партнёра считает сервер** (`backend/reports.py`) при каждом изменении студентов, выплат и партнёров. Расчёт повторяет `partnerStats` и `reportDoc` страницы: меняя одно, меняйте другое, совпадение проверяет `e2e/run.py`. В отчёт попадают только цифры и сокращённые имена; расчёт не должен падать ни на каких данных студента.
