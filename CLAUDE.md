# CRM Менти

CRM школы менторства аналитиков 1С: путь человека от заявки до оффера, платежи студентов, расчёт между владельцем, блогером и менторами. Работает на своём сервере. Интерфейс и тексты — на русском.

## Как устроено

- **`web/index.html` — вся страница CRM.** Один файл без сборки. Новые возможности делаются здесь.
- **`web/server.js` — слой данных.** Даёт странице `window.claude` (база, пользователь, скачивание файлов) поверх API сервера и `window.crmServer` (учётные записи, выход). Подключается сервером перед скриптом страницы.
- **`backend/` — сервер на Django.** Хранит записи как документы (`Doc`), проверяет права (`store.py`), отдаёт изменения по номеру ревизии, принимает заявки с сайта, загружает резервную копию.
- **`web/dev/mock.js`** — подмена `window.claude` для просмотра страницы без сервера. Страница должна работать и с ней: `window.crmServer` там нет.
- **`web/dev/calc.js`** — запускает расчёт денег кодом страницы под Node.js. Им пользуется тест сверки `test_page_and_server_calculate_the_same_reports`.
- **`web/fonts/`** — шрифт Golos Text (лицензия OFL рядом). Отдаёт `views.font` по адресу `/fonts/…`; с чужих сайтов страница ничего не загружает.

Версия страницы, опубликованная в Claude, больше не развивается. Ссылка на неё хранится в проекте Claude «CRM Менти», а не в репозитории: репозиторий публичный.

## Команды

```bash
pip install -r requirements.txt
python manage.py test backend              # тесты сервера
python manage.py makemigrations --check --dry-run
node --check web/server.js
node -e "new Function(require('fs').readFileSync('web/index.html','utf8').split('<script>')[1].split('</script>')[0])"   # синтаксис страницы
python e2e/run.py                          # сквозная проверка в браузере: сам поднимает сервер на пустой базе
```

## Как ведём разработку

Порядок работы взят из ECC (см. `.claude/ECC.md`) и подогнан под проект:

1. **План.** Для задачи крупнее мелкой правки сначала план: что меняем, какие файлы, риски, как проверим. Агент `planner` или команда `/plan`. План согласуется с владельцем до начала работы.
2. **Тест до кода**, где это возможно. Сервер: тест в `backend/tests.py`, который сначала падает. Страница: проверка в `e2e/run.py`.
3. **Реализация** минимальным изменением. Никаких функций «на вырост».
4. **Ревью** перед коммитом: `code-reviewer` для любого изменения, `django-reviewer` или `python-reviewer` для Python, `security-reviewer` для всего, что касается прав доступа, персональных данных, платежей и приёма заявок, `database-reviewer` для моделей и миграций.
5. **Проверка.** Тесты сервера и `e2e/run.py` проходят, миграции согласованы. Навык `verification-loop`.
6. **Коммит.** Работа ведётся в ветке, в `main` попадает после проверки. Push в `main` запускает тесты в GitHub и выкладку на сервер.

## Правила проекта

Если навык или агент из ECC расходится с этим разделом, действует этот раздел.

- **Тесты Django — встроенный раннер** (`manage.py test`, `django.test.TestCase`). Не переводите проект на pytest, factory_boy или DRF без запроса владельца.
- **Страница — один файл без сборки.** Не добавляйте React, сборщики и внешние библиотеки. Правило «много маленьких файлов» к ней не применяется.
- **Права проверяет сервер, а не страница.** Все правила — в `backend/store.py` (`Access`). Скрытая на странице кнопка не считается защитой: на каждое новое правило нужен тест в `backend/tests.py`, который делает запрос от имени ментора и партнёра.
- **Оплату подтверждает администратор**: ментор не отмечает платёж оплаченным, не меняет и не удаляет оплаченные (`Access._check_money`); ждать оплату, добавлять неоплаченные платежи и вносить доход он может.
- **Ментор читает и правит только своих студентов** (`mentorId` равен его записи в команде) и их встречи; встречу, куда его позвали (`mentorIds`), он видит, но не меняет; источник и долю партнёра у студента меняет только администратор. **Партнёр читает только свой отчёт.**
- **Запись идёт под блокировкой состояния** (`store.lock()`): ревизии строго растут в порядке фиксации, поэтому опрос не пропускает изменения. Любая новая запись в базу делается через `store.write`, `store.delete` или `store.system_write`.
- **На странице CRM выполняются только два скрипта**: `web/server.js` и скрипт из `web/index.html`, их хеши попадают в заголовок Content-Security-Policy. Не добавляйте второй `<script>`, обработчики в атрибутах (`onclick=`) и внешние скрипты.
- **На страницах входа и смены пароля выполняется один скрипт** — `backend/templates/backend/form.js` («показать пароль», Caps Lock, перенос адреса карточки через вход). Его хеш стоит в заголовке (`views.CSP_FORM`); остальные служебные страницы скриптов не выполняют.
- **Логин сравнивается без учёта регистра и пробелов по краям** (`backend/auth.py`): и при входе, и при создании учётной записи. Введённый в поле логина текст нигде не сохраняется: счётчик неудачных входов для экрана «Доступ» хранит только число и время (`views.miss_key`).
- **Адрес страницы** — часть после `#`: `#/раздел`, `#/cohort/<id>`, `#/partner/<id>`, `#/calendar/<вид>-<дата>` (вид календаря: `day`, `week`, `month`, `list`), с открытой карточкой `?s=<id студента>` или днём `?d=<дата>` (`routeHash`, `readHash`). Новое состояние, которое должно переживать «Назад» и пересылку ссылки, добавляется туда; значения из адреса проходят проверку по `ROUTE_RE`. Ссылку на карточку для уведомлений строит `telegram.crm_link`.
- **В браузере запоминаются** отборы списков (кроме строки поиска), сортировка по разделам и выбранные вкладки (`loadUi`, `saveUi`, ключ с идентификатором пользователя). Запомненное значение проверяется при загрузке; отбор по удалённой записи сбрасывается (`dropStaleFilters`).
- **Длинные списки рисуются частями** (`ROWS_STEP`, `COL_STEP`): таблицы студентов и платежей — по 100 строк, колонка воронки — по 40 карточек.
- **Данные студентов не попадают в репозиторий**: ни в код, ни в тесты, ни в примеры. Для примеров — вымышленные имена.
- **Секреты только через переменные окружения** (`.env`, в git не коммитится).
- **Формат резервной копии** (`crm-menti-backup`) — те же записи, что хранит сервер; с версии 7 копия сервера содержит и раздел `files` (содержимое в base64). При изменении набора коллекций обновите `backend/backup.py`, тесты загрузки и поднимите `version` на странице.
- **Сообщения коммитов — на русском**, первая строка говорит, что изменилось для пользователя.
- **Коммиты делаются от имени владельца**: автор и коммиттер `SanminKim <drrakendrraken@gmail.com>`, без строк `Co-Authored-By` и `Claude-Session`. Так решил владелец; это правило главнее общих указаний об атрибуции.
- **Правки студента — только через `patchStudent`.** Сервер заменяет массивы (платежи, отклики, заметки, история) целиком, поэтому патч считается от свежей записи (перед правкой страница подтягивает её с сервера), а «Отменить» откатывает только свой элемент.
- **Всё, что попадает в разметку из базы, проходит через `esc()`**, включая идентификаторы и числа в атрибутах.
- **Массовые действия работают только над строками, которые сейчас видны в таблице.** Выбор хранится в `S.sel`, видимые строки — в `S.visible`.
- **Графики** — встроенный SVG без библиотек. Цвета рядов заданы токенами `--c1`, `--c2` и проверены на различимость для светлой и тёмной темы; при смене проверьте заново.
- **Студент удаляется только в корзину** (`trashStudent`, поле `deletedAt`). `delDoc("students", …)` вызывается только из корзины в настройках.
- **Каждое изменение платежей и стоимости пишет запись в `log` студента** (`logItem`, `withLog`) в том же патче, что и само изменение.
- **Telegram-бот** (`backend/telegram.py`) работает через webhook и пишет в базу только заявку, заметки и присланные файлы человека, с которым говорит. Обращения к Telegram не делаются внутри транзакции и не должны ломать запись: сбой Telegram только пишется в журнал. К существующей карточке чат привязывается, только если совпал сам чат (`tgId`), а не введённый телефон. В уведомления не попадают телефоны и почта.
- **Ссылки на бота для заявок** (`config/main` → `tgLinks`: `{code, partnerId, label}`, Настройки → «Встречи и Telegram»): метка в `t.me/<бот>?start=<метка>` говорит, откуда человек. У ссылки партнёра заявка записывается за ним, у своей ссылки — с подписью в `utmSource`; удалённая метка заявку ни к кому не привязывает (`leads.link_target`). Пока список не заводили, меткой служит промокод активного партнёра. Пишет список только администратор, сервер проверяет его (`leads.links_problem`; метки `stu_` и `link_` заняты).
- **Ментор удаляется с передачей** (`mentorDeleteForm`): его студенты (и в корзине) и встречи переходят выбранному ментору или остаются без ментора, доля в направлениях с текущего месяца — ему же или владельцу (новые условия с этого месяца, прошлые не меняются), учётная запись ментора отключается. Прошлые начисления и выплаты остаются с подписью «Ментор удалён».
- **Партнёр удаляется так же** (`partnerDeleteForm`): его студенты (и в корзине) получают выбранного партнёра или остаются без партнёра, ссылки на бота переходят к нему же (без нового партнёра становятся своими с прежним именем в подписи), доля в направлениях — новому партнёру или владельцу (`moveShare`, общий для менторов и партнёров), учётная запись партнёра отключается.
- **Студент подключается к боту личной ссылкой** (`/api/telegram/student-link/`, `_link_student`): её выдаёт тот, кто ведёт студента, она одноразовая. Бот пишет студенту только в чат, у которого `TgChat.student_id` равен его карточке; одного `tgId` в записи для этого мало. Студенту уходят только напоминание о сумме платежа в день срока, напоминания о встречах и сообщения об изменении встреч.
- **Участники встречи** (`meetings.guests` на сервере, `mg` на странице): ведущий `mentorId`, приглашённые менторы `mentorIds`, студенты `studentIds` и потоки `cohortIds` (у старых встреч — `studentId`, `cohortId`, читаются так же). На занятие потока приходят его учащиеся. Сервер отклоняет кривые списки (`meetings.guests_problem`). Ментор меняет только встречу, которую ведёт сам (или без ведущего), и только если все студенты в ней его; позвать может любого ментора и только своих студентов, а весь поток зовёт только администратор (ментор не добавляет потоки, но правит занятие потока, которое ведёт; в поиске у него «все мои студенты потока»). Видят встречу ведущий, приглашённые менторы и менторы её студентов; встречу без студентов — все менторы. В форме — поле «Участники» (`pplSuggest`: поток блоком — «весь поток» и его студенты по одному).
- **Повторяющиеся встречи**: каждая — отдельная запись со знаком серии `seriesId` и правилом `repeat: {every: "day" | "week" | "2weeks", until}` (сервер проверяет: `meetings.series_problem`). Создаёт серию форма (`createSeries`, не больше `SERIES_MAX` встреч и года вперёд). У встречи из серии окно подтверждения спрашивает «Только эта / Эта и все следующие» (`applyFollowing`: дата сдвигается на столько же дней, остальное — как у этой; другая частота — следующие создаются заново; другой срок — лишние удаляются, недостающие добавляются; `deleteFollowing`). Участникам — сообщение только о ближайшей предстоящей встрече серии (её запрос идёт с `?notify=1`, остальные — без); о каждой следующей бот напоминает в её день (`meetRemind`).
- **Сообщения участникам об изменении встречи** (`meetings.notices`, `meetings.tell`): страница подтверждает изменение окном «Сохранить изменения?» с «Было → Стало» (`confirmMeet`; перенос в календаре — всегда, правка в форме и удаление — когда есть участники) и галочкой «Сообщить участникам в Telegram»; с галочкой к запросу добавляется `?notify=1`. Сервер сравнивает встречу до и после и пишет каждому участнику, что изменилось для него: приглашение (студенту с кнопками «Буду / Не буду»), перенос «было → стало», новое название или ссылка, «вы больше не участвуете», отмена или удаление. О прошедших встречах и автору изменения не пишет; студентам — только если у встречи не выключено `remind`. Сообщения готовятся в транзакции, а уходят после фиксации в фоновом потоке (`dispatch`).
- **Напоминания студентам о встречах** (`backend/meetings.py`, `scheduler._student_meetings`): утром в день встречи и за `before` минут до начала, со ссылкой (встречи или постоянной ссылкой потока `cohort.link`) и кнопками «Буду» / «Не буду». Ведущему и приглашённым менторам напоминание приходит за час. Участники — студенты встречи и учащиеся её потоков (этапы группы `study`); то же правило на странице (`meetPeople`). Ответы лежат во встрече (`rsvp`: id студента → `{a: "yes" | "no", at}`), записывает их только бот (`record_answer`); ментору менять `rsvp` запрещено (`Access.check_write`). Настройки — `config/main` → `meetRemind`, по умолчанию выключены; у встречи `remind: false` отключает её напоминания.
- **Файлы от студента** (фото начисления зарплаты, отработанных часов) бот записывает в `proofs` карточки как ссылку на файл в Telegram; сам файл на сервере не хранится и читается по запросу (`/api/telegram/file/…`, `telegram.fetch_file`). Добавляет записи только бот: ментор может убрать запись, но не вписать свою (`Access._check_proofs`). Файл отдаётся с `nosniff` и CSP `sandbox`, PDF — только скачиванием.
- **Договор и файлы к платежам** (`backend/files.py`, модель `FileBlob`): содержимое лежит в базе зашифрованным (ключ выводится из `SECRET_KEY`: при его смене прежние файлы читаются только из ночной копии), в записи студента — только сведения `{id, name, mime, size, at, by}` в `contract` и `payments[i].files`. Эти сведения пишет только сервер при загрузке и удалении (`POST /api/files/`, `DELETE /api/files/<id>/`); правка студента со страницы их не меняет (`files.keep` в `store.write`), файлы удалённого платежа и удалённого насовсем студента стираются (`files.prune`, `forget_student`). Файлы видит и прикрепляет тот, кто ведёт студента; к оплаченному платежу файлы добавляет и убирает только администратор; партнёру файлы недоступны. Тип определяется по содержимому (`files.sniff`: PDF, JPG, PNG, WebP, DOC, DOCX), до 10 МБ, отдаётся с `nosniff` и CSP `sandbox`, картинки — во вкладке, остальное — скачиванием. В ночную копию файлы попадают, пока помещаются в `backup.FILES_IN_BACKUP` (договоры первыми); копия, скачанная со страницы, файлов не содержит.
- **Карточка студента** (`drawerHTML`): сверху путь, «Дальше», следующий шаг и «О студенте» (`about`), ниже вкладки `CARD_TABS` (Главное, Договор и оплаты, Обучение, Работа, История; `S.cardTab`, при открытии другой карточки — «Главное»). Данные платежа (способ оплаты, номер чека) — поле `details` платежа.
- **Календарь** (`calendarView`) показывает только встречи (собеседования, шаги и платежи — на экране «Сегодня» и в карточке студента) и устроен как почтовые календари: слева «+ Встреча», маленький месяц и выбор ментора, справа неделя или день по часам (`weekHTML`), месяц (`monthHTML`) или список на две недели (`listHTML`); на компьютере по умолчанию неделя, на телефоне — день. Встречи без времени стоят в строке «Весь день» (`calItems`). Цвет блока выбирают у встречи (поле `color`, ключ из `MEET_COLORS`; пусто — цвет по типу): в быстрой форме, в карточке встречи и в полной форме. В разметку попадает только ключ из списка, цвета заданы токенами `--mc-*` для светлой и тёмной темы. Нажатие на свободное время или протяжка — быстрая встреча (`quickMeet`: название, дата и время «с–по», цвет), перетаскивание встречи — перенос (в месяце — на другой день, время сохраняется), нижний край — длительность, в карточке встречи — поля даты и времени, которые сохраняются при закрытии карточки (`takeMove`, `commitMove`; конец сдвигается вместе с началом), всё через `moveMeet` с подтверждением и «Отменить»; пальцем — после удержания. Пока встречу создают или меняют её время в карточке, она уже видна в сетке на своём месте и своего размера с длительностью (`GHOST`, `drawGhost`; переживает перерисовку, прежнее место бледнеет); в полной форме под длительностью — «Займёт 13:00–14:30 · 1 ч 30 мин» (`meetSpan`). Пересекающиеся встречи встают рядом и растягиваются вправо на свободное место (`layoutDay`); узкий блок показывает только название (`narrow`). Переносить можно только то, что разрешает сервер (`canMove` повторяет `Access.check_write`). Пока идёт перетаскивание, перерисовка откладывается (`CALDRAG`, `CALRENDER`).
- **Платёж от дохода** (почасовая оплата) хранится без суммы: `amount: null` и `percent`. Сумму вносит сотрудник формой «Указать доход» (`incomeForm`); бот у студента доход только спрашивает и в платежи ничего не пишет. Код, читающий `amount`, должен переносить `null` (`nnum`, `_number`).
- **Дела по расписанию** (`backend/scheduler.py`, команда `tick --loop`, служба `scheduler` в docker-compose): утренняя сводка, напоминание о встрече, ночная копия базы администратору. Каждое дело отмечается в кэше и не повторяется. В Telegram уходят только числа, названия встреч и время. База отправляется только зашифрованной (`backup.encrypt`, пароль `BACKUP_PASSPHRASE`); без пароля копия не отправляется вовсе.
- **Деньги делятся по направлениям** (`directions`). Чистая выручка направления за месяц = оплаты его студентов (по дате оплаты) минус расходы (`expenses`); каждая сторона из условий направления (партнёр или ментор) получает от неё свой процент, остаток — владельцу. Студент относится к направлению своего потока (`cohort.directionId`). Условия (`terms`) действуют с месяца `from`: смена ставок не пересчитывает прошлое. Выплаты лежат в `payouts` с `partnerId` или `mentorId`. Оплаченный платёж помнит направление, в котором получены деньги (`dirId`, ставит сервер в `store._pin_payments`, страница — `markPaid`; старые оплаты отмечает команда `pin_payments` при старте): перевод студента в другой поток или потока в другое направление прошлое не меняет. Деньги студентов из корзины остаются в расчёте. Возврат — платёж с минусом и `refund: true` в месяце возврата (`refundForm`). Доли сторон в одном условии вместе не больше 100% (`reports.terms_problem`, проверяется при записи).
- **Расчёт сделан дважды и обязан совпадать**: `settle`, `partyStats`, `partyReport` на странице и `settle`, `_money`, `build` в `backend/reports.py`. Меняя одно, меняйте другое. Совпадение проверяют тест сервера `test_page_and_server_calculate_the_same_reports` (60 случайных баз с кривыми записями, код страницы запускается в Node.js через `web/dev/calc.js`; идёт в GitHub при каждом push) и `e2e/run.py`. Числа разбираются одинаково (`nnum` и `_number`), записи складываются в порядке идентификаторов.
- **Направления, расходы и выплаты читает только администратор.** Ментор и партнёр видят свои начисления в отчёте `reports/<id своей записи>`, который считает сервер; чужой отчёт не открывается даже при совпадении идентификаторов (сверяется `kind`). В отчёт ментора попадает и состав расходов (`_expenses`: дата, сумма, комментарий, направление) — только тех месяцев и направлений, где у него есть доля; партнёру состав расходов не показывается.
- **Этапы воронки настраиваются** (Настройки → «Воронка и этапы», `config/main` → `stages`). Разбор списка сделан дважды и обязан совпадать: `stageList` на странице и `reports.stage_list` на сервере (кривые записи пропускаются, без открытых этапов — этапы по умолчанию `DEFAULT_STAGES` / `reports.STAGES`; совпадение по умолчанию проверяет `test_stage_list_matches_the_page`, по случайным спискам — тест сверки). Пишет список только администратор, сервер отклоняет мусор (`reports.stages_problem`). Логика опирается не на идентификатор этапа, а на его свойства: группа (`sales`, `study`, `job`, `closed` — доска, напоминания о занятиях для `study`, отказ с причиной для `closed`), `ask` (что спросить при переходе: `note`, `call`, `payment`, `study`, `offer`), `employed`, `next` (шаг по умолчанию). Первый этап пути получает новые заявки (в том числе с сайта), последний означает «путь пройден». Удаляя этап, страница сначала переводит людей с него (`stageDeleteForm`); на неизвестном этапе человек виден с подписью «Этап удалён». Отчёт партнёра отдаёт и подписи этапов (`stageLabel`): партнёр настроек не читает.
- **Настройки сгруппированы** (`SET_GROUPS`, `S.setTab`): воронка и этапы, команда и партнёры, деньги, встречи и Telegram, данные, мой профиль. Ментор видит только профиль и корзину. Списки подсказок (`lostReasons`, `stepHints`, `meetHints`, `expenseHints`), текст напоминания о платеже (`payRemind`), срок «застрял» (`stuckDays`) и оплата с зарплаты по умолчанию лежат в `config/main`; пустое значение — значение по умолчанию.
- **Проверка работы** (`backend/health.py`): `/health/` открыт без входа и отдаёт только «ok» или общую причину сбоя, без данных. Планировщик на каждом проходе ставит отметку «жив» и раз в 5 минут открывает `/health/` по внешнему адресу, а результат отправляет на `HEALTHCHECK_PING_URL` (Healthchecks.io). Сигнал о сбое идёт через внешний сервис, а не через свой бот: свой бот падает вместе с сервером.
- **Отчёты считает сервер** (`backend/reports.py`) при изменении оплат, потоков, направлений, расходов, выплат, партнёров и команды. В отчёт попадают только цифры и сокращённые имена; расчёт не должен падать ни на каких данных.
- **Связка с платформой курсов** описана в `INTEGRATION.md` (тот же файл лежит в репозитории платформы `SanminKim/on_ass_platform`). CRM главная по людям, этапам, потокам и деньгам, платформа — по обучению. Обращается только CRM: подписанные запросы по HTTPS, на платформу не уходят контакты и оплаты.
